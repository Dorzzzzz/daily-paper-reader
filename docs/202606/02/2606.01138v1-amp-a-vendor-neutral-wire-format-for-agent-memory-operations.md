## 摘要
智能体记忆框架——mem0、Letta/MemGPT、Cognee、Zep/Graphiti、MemoryOS、MemTensor——各自拥有独立的SDK、存储布局和操作词汇。目前不存在共享的线格式：每次集成都是定制化的，每次迁移都需要从头重建记忆，也没有框架提供治理界面让人在写入长期存储前进行审查。我们提出memorywire，一种基于JSON-Schema 2020-12的线格式，支持四种记忆类型（语义、情景、程序、情感）上的五种记忆操作（记住、回忆、遗忘、合并、过期），并包含一个MemoryStore接口、一个扇出路由器以及一个可选的人机回环治理通道。我们描述了一个开源参考实现，包含五个后端适配器（sqlite-vec、mem0、Letta、Cognee、pgvector）；在一个包含100个事实/50个查询的标注语料库上的微基准测试中，42个标注查询的recall@5达到1.000，摄取p50为37.8毫秒，回忆p50为40.6毫秒；一个对抗融合实验表明，在1-of-N排名为0的注入扫描（K ∈ {0,5,...,50}）中，倒数排名融合（RRF）保持recall@5=1.000，而最大融合在K≥5时下降至0.500且泄露率达80%；以及一个包含16个场景的跨适配器一致性测试套件，80个测试单元中通过68个，零失败。该贡献并非新算法，而是将已有组件（RRF、有限状态机、短期/长期记忆整合、差异-批准工作流）封装为一种与供应商无关的协议，并附有经验验证的参考实现，旨在与模型上下文协议（Model Context Protocol）协同而非竞争。

## Abstract
Agent-memory frameworks - mem0, Letta/MemGPT, Cognee, Zep/Graphiti, MemoryOS, MemTensor - each ship their own SDK, storage layout, and operational vocabulary. There is no shared wire format: every integration is bespoke, every migration rebuilds memory from scratch, and no framework ships a governance surface that lets a human review writes before they enter long-term storage. We present memorywire, a JSON-Schema 2020-12 wire format for five memory operations (remember, recall, forget, merge, expire) over four memory types (semantic, episodic, procedural, emotional), with a MemoryStore interface, a fan-out router, and an optional HITL governance channel. We describe an open-source reference implementation with five backend adapters (sqlite-vec, mem0, Letta, Cognee, pgvector); a microbenchmark on a 100-fact / 50-query labelled corpus achieving recall@5 = 1.000 on the 42 labelled queries with ingest p50 = 37.8 ms and recall p50 = 40.6 ms; an adversarial-fusion experiment showing Reciprocal Rank Fusion holds recall@5 = 1.000 across a 1-of-N rank-0 injection sweep (K in {0,5,...,50}) where max fusion collapses to 0.500 with 80% leak at K >= 5; and a 16-scenario cross-adapter conformance suite passing 68 of 80 cells with zero failures. The contribution is not a new algorithm; it is a packaging of established components (RRF, FSMs, STM/LTM consolidation, diff-and-approve workflows) into a venue-neutral protocol with an empirically validated reference, positioned to compose with the Model Context Protocol rather than compete with it.

### 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：定义一个 JSON-Schema 2020-12 的线格式，包含：
    - **五种操作**：`remember`（写入）、`recall`（读取）、`forget`（删除）、`merge`（合并去重）、`expire`（基于 TTL 过期策略）。
    - **四种记忆类型**：semantic（语义事实）、episodic（情景事件）、procedural（程序/FSM 编码）、emotional（情感关联）。
    - **MemoryStore 接口**：后端适配器需实现该接口，并声明 `capabilities`（如 vector、fts、graph 等），供路由器按需调度。
    - **扇出路由器（MemoryRouter）**：并行发送操作到多个后端 store，并支持三种融合算法：
        - **RRF（默认）**：`score(d) = Σ_i 1/(k + r_i(d))`，其中 `k=60`，排名 `r_i(d)`。该算法与原始分数无关，对恶意后端具有健壮性。
        - **MAX**：取所有 store 中最高原始分数。
        - **WEIGHTED**：按配置权重加权求和。
    - **可选治理通道（Governance Channel）**：对 `remember`、`forget`、`merge` 操作，可通过 `approval_required=true` 标记，将写入暂时挂起（使用 `deleted_at=-1` 哨兵），等待人类通过 UI 审查 diff、审批或拒绝后才会生效。
- **关键技术细节**：
    - 所有操作请求/响应均对应 JSON Schema 文件，严格验证。
    - 支持异步优先（`async def`），使用 `asyncio.gather(return_exceptions=True)` 实现部分容错——单个后端失败不影响整体操作。
    - 程序性记忆（procedural）采用 pytransitions 的 FSM 序列化表示，并做了安全限制（禁止 `before/after/prepare` 等可能导致 RCE 的键）。
    - STM↔LTM 转换器：后台异步任务，定期对短期记忆窗口评分（基于新颖性、显著度、置信度），将高分项提升为长期记忆（类型改为 semantic），并淘汰冷门项。

### 3. 实验设计

- **微基准测试（Microbenchmark）**：
    - **数据集**：100 个人工编写的事实，横跨 10 个用户和四种记忆类型；50 个查询（24 个释义查询、10 个精确/接近匹配、8 个多命中查询、8 个无匹配探针）附带黄金 ID 标签。
    - **Embedder**：`sentence-transformers/all-MiniLM-L6-v2` (384维，CPU 推理)。
    - **后端**：sqlite-vec（`:memory:`），执行 intra-store RRF（结合 vec0 ANN 和 FTS5 关键词搜索）。
    - **指标**：Recall@5、Precision@5、延迟 p50/p95/p99。
- **对抗融合实验（Adversarial Fusion Experiment）**：
    - **场景**：3 个子 store（2 个良性 + 1 个恶意）。恶意 store 进行 rank-0 注入攻击，返回 K 个攻击者控制 ID（K ∈ {0,5,10,…,50}）。
    - **语料**：50 个合成记忆，20 个查询，每个查询有 2 个黄金 ID。
    - **对比方法**：RRF vs. MAX vs. WEIGHTED（等权重）。
    - **指标**：Recall@5（对黄金集）和攻击者 ID 泄露率。
- **跨适配器一致性测试（Cross-Adapter Conformance Suite）**：
    - **场景数**：16 个协议不变性场景（如 basic_remember_recall、type_filter、forget_by_ids、expire_by_age 等）。
    - **适配器**：sqlite-vec、mem0、Letta、Cognee、pgvector。
    - **结果统计**：80 个单元格（16×5），记录 PASS / SKIP / FAIL。
- **初步 LongMemEval 和 LoCoMo**（附录部分）：
    - 两个基准数据集的各 10-12 个问题，1 个种子，LLM-as-judge（gpt-4o-mini），后端 sqlite-vec。

### 6. 论文的主要结论与发现

- **微基准**：在 42 个标注查询上 Recall@5 = 1.000，Precision@5 = 0.214（因多数查询仅 1 个黄金 ID），摄取 p50 = 37.8 ms，回忆 p50 = 40.6 ms。8 个无匹配探针均返回空结果（但返回了 top-k 充实，因无校准阈值）。
- **对抗融合**：RRF 在整个 K 扫描中保持 Recall@5 = 1.000（攻击者泄露率始终为 0）；MAX 在 K=5 时 Recall@5 下降至 0.500，泄露率 80%；WEIGHTED（等权重）表现与 RRF 相同。
- **一致性测试**：80 个单元格中 PASS 68 / SKIP 12 / FAIL 0。SQL 后端（sqlite-vec、pgvector）全通过；SDK 包装适配器存在三类缺口（无用户 ID 命名空间、无空策略守卫、无稳定记录 ID），为 v0.2 规范收紧提供了依据。
- **主要结论**：将已有组件标准化为供应商无关线格式是可行的，RRF 能有效抵御恶意后端注入攻击，一致性测试验证了协议的互操作性。memorywire 可与 MCP 组合使用，不构成竞争。

### 7. 优点

1. **设计思路清晰**：遵循“小表面、Schema 固定、无状态、异步优先”原则，线格式简洁（5 操作 4 类型 1 治理通道）。
2. **安全设计周密**：RRF 的分数无关性从根本上抵抗恶意后端注入；治理通道（diff-and-approve）将人类审查嵌入标准流程；FSM 过程中做了 RCE 防护（禁止回调键）。
3. **实际验证充分**：通过跨适配器一致性测试明确量化了不同框架的兼容性缺口，并据此提出规范改进方向，体现了开放迭代的态度。
4. **开源实现完整**：提供参考实现（Python）、5 个后端适配器、治理 UI、威胁模型文档，可复现所有实验。
5. **与 MCP 关系处理得当**：明确阐述了“作为独立线格式而不是 MCP 子协议”的原因——迭代速度、多协议可移植性；同时提供了三种组合模式，体现了生态友好性。

### 8. 不足与局限

1. **实验规模不足**：
    - 微基准仅 100 条记录，对抗融合仅 50 条记录，长时记忆基准仅 10-12 个问题/种子，样本量过小，统计意义有限。
    - 未在百万级记录、分布式部署、真实网络延迟下测试；所有结果来自单机 CPU 环境。
2. **数据集和评价的人工性**：
    - 微基准语料手工编写，对抗融合的“攻击者知己知彼”（知道 over-fetch 参数），实际黑盒攻击效果未知。
    - 长时记忆基准使用单一 LLM 评分器（gpt-4o-mini），无人类校准，绝对分数不可跨论文比较。
3. **安全模型的局限性**：
    - 未覆盖“多数后端被攻陷”（n_adversarial ≥ n_benign）时 RRF 共识失效的场景。
    - 治理 UI 目前使用全局 Bearer Token，无 per-agent ACL；审计日志未采用 Merkle 链（仅通过代码维护追加性）。
4. **协议成熟度**：
    - v0 版本明确保留破坏兼容性的权利（v0.5 前可能 break），且嵌入器选择、召回阈值控制等关键细节尚未标准化。
    - 用户研究（NASA-TLX、IRB 流程）尚未进行，治理 UI 的实际可用性缺乏量化评估。
5. **作者作为评估者**：实验均由作者本人完成，未经过第三方独立审计，存在确认偏差风险。
6. **对 LLM 层面攻击无能为力**：若上游 LLM 被提示注入产生虚假记忆，memorywire 只能忠实存储和返回，无法区分真假——只能审计，无法预防。

总结来看，这篇论文**在标准化和安全性设计方面做出了扎实贡献**，但**实验支撑尚显薄弱**，其实际应用价值需在更大规模、更具挑战性的场景中进一步验证。
