## 摘要
个性化AI智能体需要用户记忆：一种跨多次对话构建并在每次新对话中参考的、关于用户身份的持久模型。如今，这种记忆几乎总是以非结构化文本、知识图谱或扁平化事实存储的形式存在，并通过检索——获取与当前请求最相似的条目——来调用。这种“事实袋”记忆能很好地回忆单个事实，但由于存储事实与执行操作是分离的步骤，它在解决矛盾、聚合多条记录或强制执行规则方面存在困难。我们认为用户记忆应该是可执行的。我们提出“用户即代码”（UaC）范式，其中智能体对用户的模型是一个活跃的软件项目：类型化的Python对象持有用户状态，普通Python函数编码管理这些状态的规则，因此在同一介质中表示和推理用户可由解释器运行。其实现机制是一个两阶段流水线：一个仅追加的日志从不丢弃任何事实，并定期检查点化为类型化代码。这改变了记忆的能力。在标准长期对话基准测试中，UaC在召回率上匹配了全上下文上限和最强的先前记忆系统（LOCOMO上78.8%）。其优势在表征至关重要的地方显现。在关于用户历史的聚合问题——“我去年出国旅行了多少次？”——基于检索的记忆崩溃（6-43%），而UaC保持近乎完美（99%），因为答案是对类型化状态的一行计算，而非对文本的搜索。并且由于其规则在状态变化时确定性执行，UaC能呈现未经请求的、安全关键的警报——如新处方的药物与数月前记录的过敏冲突——这是查询驱动记忆无法提供的功能。

## Abstract
A personalized AI agent needs a user memory: a persistent model of who the user is, built across many conversations and consulted on each new one. Today this memory is almost always stored as unstructured text, a knowledge graph, or a flat store of facts, and consulted by retrieval -- fetching the entries most similar to the current request. Such "bag-of-facts" memory recalls individual facts well, but because storing a fact and acting on it are separate steps, it struggles to resolve contradictions, aggregate over many records, or enforce rules. We argue that user memory should instead be executable. We introduce User as Code (UaC), a paradigm in which an agent's model of a user is a living software project: typed Python objects hold the user's state and ordinary Python functions encode the rules that govern it, so representing and reasoning about the user happen in one medium an interpreter can run. The enabling mechanism is a two-phase pipeline: an append-only log that never discards a fact, periodically checkpointed into typed code.   This changes what memory can do. On standard long-term conversation benchmarks, UaC matches both a full-context upper bound and the strongest prior memory systems on recall (78.8% on LOCOMO). Its advantage emerges where representation matters most. On aggregate questions over a user's history -- "how many international trips did I take last year?" -- retrieval-based memory collapses (6-43%) while UaC stays near-perfect (99%), because the answer is a one-line computation over typed state rather than a search over text. And because its rules execute deterministically whenever the state changes, UaC can surface unsolicited, safety-critical alerts -- such as a newly prescribed drug that conflicts with an allergy recorded months earlier -- a capability query-driven memory cannot provide.

### 1. 论文的核心问题与整体含义（研究动机和背景）

*   **核心问题**：当前个性化AI智能体的“用户记忆”系统存在根本性缺陷。它们通常以非结构化文本、知识图谱或扁平化事实列表的形式存储信息，并通过相似度检索（RAG）来获取。这种“事实袋”（Bag-of-Facts）模式虽然能很好地回忆孤立事实，但在处理需要**逻辑推理、矛盾解决、数据聚合和规则执行**的高级任务时显得力不从心。例如，它无法自动判断“新开的抗生素是否与数月前记录的青霉素过敏冲突”，也无法轻易回答“去年我出国旅行了多少次？”这类需要汇总计算的问题。
*   **研究背景**：个性化AI代理依赖于对用户模型（User Model）的持久记忆。现有记忆系统（如Mem0, A-MEM, MemMachine等）将事实存储与逻辑验证（Verification）分离。一个事实被存储后，代理必须通过另一次LLM调用来理解、推理并执行规则，这个过程不仅效率低，且极易出错。
*   **整体含义**：论文提出了一种颠覆性的范式——将用户记忆视为**可执行的代码**（Executable Code）。这意味着用户的状态和规则不再是需要LLM每时每刻去“阅读理解”的文本，而是可以被Python解释器直接操作、精确计算的程序。这一转变从根本上弥合了“存储事实”与“使用事实”之间的鸿沟，将记忆从一个被动的、近似检索的数据库，转变为一个主动的、确定性执行的程序。

### 2. 论文提出的方法论：核心思想、关键技术细节

*   **核心思想**：“用户即代码”（User as Code, UaC）。将用户的个人信息、偏好、历史记录等抽象为一个活的、模块化的软件项目。用户状态由类型化的Python数据类（Typed Python Dataclass）表示，而管理这些状态的规则则由普通的Python函数编码。这样，用户信息的表示和基于此的推理都在同一介质（可执行的Python代码）中完成。
*   **关键技术细节：两阶段流水线**
    1.  **第一阶段：记忆（Memorize）—— 仅追加的事实提取**
        *   **过程**：每轮对话后，一个LLM会提取所有原子事实，并将它们作为纯文本字符串**追加**到一个永不覆写的日志列表中。
        *   **关键操作**：所有相对日期（如“昨天”）会被解析为绝对日期，以增强时间推理的准确性。
        *   **目的**：**保证信息零丢失**，为下游的结构化提供完整的数据源。
    2.  **第二阶段：结构化（Structure）—— 周期性代码生成**
        *   **过程**：定期（例如每N次对话后），另一个LLM会基于当前完整的、仅追加的事实日志，**重新生成**整个结构化Python代码。这个“检查点”过程会创建类型化的数据类实例、领域模块（如`travel/`, `health/`）和约束函数。
        *   **关键设计**：代码是**从完整的语料库中重新生成**，而不是增量编辑。这避免了因编辑式更新而导致早期事实被破坏或丢失的信息损失问题（Ablation证实这是+12.3pp的关键）。
    3.  **检索与使用**
        *   **多策略检索**：在回答用户问题时，UaC结合三种信息源：
            1.  **结构化代码状态**：主要信息源，直接包含类型化的Python对象。
            2.  **事实向量检索**：回退到原始事实日志，通过向量相似性检索，以覆盖未能完全类型化的细节事实。
            3.  **原始对话档案检索**：进一步回退，保留下游问题所需的原始措辞。
        *   **生成-验证-审查循环**：这是实现主动服务（Active Service）的核心。LLM“编码代理”会编写Python约束条件（Constraints），这些约束在沙盒中确定性执行，结果被审查并可能固化为持久的警报（`ACTIVE_ALERTS`）。如检测到药物冲突的代码，会作为预计算警报在每个会话开始时呈现，无需用户提问。

    *   **分析推理**：在需要统计计算（如“去年出国旅行次数”）时，检索式记忆系统（如MemMachine, Mem0）准确率分别跌至43%和6%，而UaC凭借对类型化代码的精确计算，准确率达99%。
    *   **主动服务**：UaC在标准主动服务场景中达到100%的警报率，远超无预计算警报的基线（52.5%）。其确定性执行约束的能力是检索式记忆无法比拟的。
3.  **架构的关键是“记忆”与“结构化”分离**：消融实验证明，**仅追加的事实提取**是提升召回率的最强单一因素（+19pp），而**周期性重生成代码**而非增量编辑是避免信息丢失、实现结构化优势的关键（+12.3pp）。
4.  **代码结构对纯召回任务贡献较小**：通道消融表明，UaC在LOCOMO上的优异表现主要归功于事实向量和原始档案检索通道，结构化的代码状态在纯召回任务中几乎冗余（-1.3pp, p=0.67）。这强调了UaC的设计并非为了“更好”地检索孤立事实，而是为了解锁**新类型**的记忆能力。

### 7. 优点

*   **方法论的创新性**：将用户记忆建模为可执行代码是一个极具洞察力的转变，解决了长期困扰该领域的事实与规则分离的核心问题。
*   **实验设计的严谨性和全面性**：实验设计非常出色，不仅评估了标准任务，还创造性地设计了新的基准（分析推理、主动服务）来展示UaC的独特优势。大量消融和鲁棒性分析使结论非常可靠。
*   **公开与诚实的分析**：论文不回避系统缺陷，坦诚地分析了UaC的不足，如对单跳召回的贡献有限、写入开销、以及自身性能瓶颈（如代码生成CAP）。这种诚实大大增加了结果的可信度。
*   **基于Sutton的“苦涩教训”的设计哲学**：论文明确表示，其避免手工设计固定模式，而是依赖LLM在代码生成方面的最强能力来动态创建数据结构，这是一个具有前瞻性的设计选择。

### 8. 不足与局限

1.  **写入开销**：UaC需要两轮LLM调用（事实提取+代码结构化），比一对一的事实系统多一倍。对于需要极低延迟写入的场景，这可能是一个瓶颈。
2.  **结构化状态对纯回忆的贡献有限**：如通道消融所示，如果只需要回答简单的、单跳的事实性问题，UaC的结构化步骤带来的额外成本可能不值。其价值主要体现在**无法被检索解决的复合型任务上**。
3.  **主动服务依赖于流水线**：没有生成-验证-审查循环生成的预计算警报，UaC的主动服务能力会大幅下降（52.5%）。这表明该功能的全部潜力并非仅依赖可执行表示，而是依赖整个管道。
4.  **可扩展性挑战**：当前的“一次性重生成”策略面临可扩展性问题。在超过约100个会话后，输入上下文可能溢出，导致早期事实被截断（输入被硬限制在500K字符）。论文已将此列为未来工作（分层式结构化）。
5.  **复现的保真度与基础设施差异**：对现有SOTA的复现虽然尽量忠实，但仍替换了其原始的基础设施（如矢量化数据库），这可能导致性能差异。虽然作者已坦诚说明，但仍需谨慎解读这些结果是SOTA架构的“下限”。
6.  **安全与沙盒需求**：将用户状态作为可执行代码存储需要严格的沙盒和隔离机制，以防止代码注入和跨用户泄漏，增加了部署的复杂性。
7.  **主动服务“困难”场景统计不显著**：在20个困难主动服务场景中，UaC与实时Mem0的差距未能达到统计显著性，表明在复杂推理任务上，UaC的优势虽然仍在，但差距可能不如想象中大，且受制于小样本。
