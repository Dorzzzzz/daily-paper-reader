## 摘要
LLM在智能体记忆流水线中的位置——介于召回平面（检索存储的事实，已广泛基准测试）和控制平面（通过取代、释放、清除来变异事实，基本未测试）之间——决定了系统能恢复哪些遗忘故障模式。通过在385个对抗性案例上比较十三种系统配置，我们观察到三种布局模式具有部分互补的覆盖率：确定性基元足以处理词法/时间类别，但在规范化方面失败（标识符混淆5%，跨语言0%）；写入时LLM可恢复规范化（100%），但无法处理意图感知删除（前缀碰撞和复合事实0%）；变异时钩子可恢复意图感知删除（78-85%），并同时提升几乎所有类别（总体91.7-93.2%，每次385例运行成本0.17美元，变异延迟2.3秒/例对比确定性64-191毫秒/例，召回路径不变）。我们通过ForgetEval（一个1000例模板套件加385例对抗层（132例手工+253例LLM起草经预言验证），由确定性子串匹配评分，配以一个六方法适配器协议（诚实N/A评分，允许异构存储以130行代码接入））揭示了这一权衡。接纳性由10名标注者IAA（Fleiss' kappa = 0.958）和一个77例外部作者子集（四名匿名贡献者）证实，该子集复制了规范化不对称性并放大了联合布局提升（+27.8个百分点）。生产故障主要是遗忘故障而非召回故障，但现有基准仅衡量召回。ForgetEval和所有适配器均以MIT许可证发布。

## Abstract
Where an LLM sits in an agent memory pipeline -- between the recall plane that retrieves stored facts (extensively benchmarked) and the control plane that mutates them via supersede, release, purge (largely untested) -- shapes which forgetting failure modes the system recovers. Comparing thirteen system configurations on a 385-case adversarial surface, we observe three placement regimes with partly complementary coverage: deterministic primitives suffice for lexical/temporal categories but fail canonicalization (5% on identifier-obfuscation, 0% on cross-lingual); inscribe-time LLM recovers canonicalization (100%) but cannot help intent-aware deletion (0% on prefix-collision and compound-fact); a mutation-time hook recovers intent-aware deletion (78-85%) and brightens nearly all categories simultaneously (91.7-93.2% overall, $0.17 per 385-case run, 2.3s/case mutation latency vs. 64-191ms/case deterministic, recall path unchanged).   We expose the trade-off via ForgetEval, a 1000-case templated suite plus a 385-case adversarial layer (132 hand-crafted + 253 LLM-drafted oracle-validated) scored by deterministic substring match, paired with a six-method Adapter Protocol with honest N/A scoring that lets heterogeneous memory stores enter in 130 lines. Admission is corroborated by 10-annotator IAA (Fleiss' kappa = 0.958) and a 77-case external-authored subset (four blind contributors) that replicates the canonicalization asymmetry and amplifies the joint-placement lift (+27.8 pt). Production failures are predominantly forgetting failures rather than recall failures, yet existing benchmarks measure only recall. ForgetEval and all adapters are released under MIT.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：现有智能体记忆基准（如 LongMemEval、MTEB、BEIR、LOCOMO）只评测**召回（recall）** 能力，但在实际生产环境中，主要的失败模式是**遗忘（forgetting）** 故障——例如轮换后的密码仍被推荐、GDPR 删除记录仍在候选池、矛盾的工作头衔跨会话出现。这些是控制平面（修改存储器）的缺陷，而非召回平面的问题。
- **背景**：LLM 在记忆流水线中的**放置位置**（位于召回平面与控制平面之间）决定了系统能恢复哪些遗忘失败模式。目前缺乏对这一“遗忘轴”的系统基准测试和架构研究。已有工作（如 Hu et al. 2026 的 FactConsolidation）仅测试单一事实取代，粒度不够；Uddin et al. 2026 的 FAMA 提供聚合指标但未分解原语层面。
- **整体含义**：本文通过对比 13 种系统配置（6 种放置体制），揭示了 LLM 放置位置对遗忘恢复能力的决定性影响，并提出了首个针对记忆存储原语的遗忘基准 ForgetEval 和可复用评估协议，填补了生产级遗忘评估的空白。

## 2. 方法论：核心思想、关键技术细节

### 2.1 核心思想
- **遗忘分解**：将遗忘能力拆分为 5 个结构族（取代 supersession、衰减 decay、失忆 amnesia、清除 purge、漂移 drift）和 10 个攻击类别（如子串陷阱、前缀碰撞、跨语言标识符等）。
- **放置体制**：对比三种 LLM 放置策略：
  - **确定性原语**（无 LLM）：全模板/词汇匹配。
  - **写入时 LLM**（inscribe-time LLM）：在写入时用 LLM 提取标签/实体链接（如 A-MEM、MEM0+v3）。
  - **变异时钩子**（mutation-time LLM hook）：在修改（取代/释放/清除）时调用 LLM 做规划（如 Lethe+LLM、LangGraph+LLM）。
- **Adapter 协议**：6 方法行为契约（reset, inscribe, recall_texts 为基础方法；supersede, release, purge 为可选方法，可允许 N/A 评分），任何存储后端实现该协议即可用同一套基准公平比较。

### 2.2 关键技术细节
- **ForgetEval 基准**：共 1385 个案例（1000 个模板 + 385 个对抗性案例）。385 个对抗案例中，132 个手工编写（核心），253 个由 LLM 起草并经预言验证（oracle-validated）。评分使用确定性子串匹配（top-10 召回中必须包含某字符串且不能包含另一字符串），无需 LLM 裁判参与评估循环。
- **评估协议**：
  - 两阶段接纳：阶段1结构过滤（格式正确、无自困陷阱）；阶段2 独立 LLM 裁判（Qwen-2.5-72B）验证案例可解答性。
  - 多方验证：10 名标注者 IAA（Fleiss’ κ = 0.958），跨模型族裁判核对（Claude Opus 4.7 与人类一致率 99/100）。
- **对抗类别**：子串陷阱、前缀碰撞、释义取代、否定陷阱、时间限定、共享属性、复合事实（partial-edit）、标识符混淆、跨语言标识符、递归取代。
- **参考实现**：附带一个基于 SQLite + sqlite-vec + FTS5 的参考存储（~700 行 Python），实现所有 6 个协议方法，并可选 LLM 钩子。

## 6. 主要结论与发现

1. **LLM 放置位置决定遗忘能力**：确定性原语在词法/时间类别上足够，但无法处理规范化（标识符混淆仅 5%，跨语言 0%）；写入时 LLM 恢复规范化（100%），但无力进行意图感知删除（前缀碰撞 0%，复合事实 0%）；变异时钩子同时恢复意图感知删除（78-85%）并显著提升几乎所有类别（总体 91.7-93.2%，仅排除复合事实后 93.3-94.2%）。
2. **三种放置模式互补而非冗余**：没有一种模式能覆盖所有故障模式。联合放置（写入时+变异时）效果更优（Letta+LLM 提升+27.8 pt 在外部子集）。
3. **架构无关性**：同一变异时钩子应用在 Lethe 和 LangGraph 上结果一致，证明提升来自钩子模式而非特定存储原语。
4. **召回-遗忘折中**：Lethe（遗忘强）和 LangGraph（召回强）在样本中形成非支配点；MEM PALACE 被 LangGraph 支配。变异时钩子提升遗忘轴而不改变召回。
5. **现有基准缺失遗忘轴**：Memora（召回-遗忘双评估）与 ForgetEval 互为补充，存在轴翻转（MEM PALACE 在 ForgetEval 上 0%，在 Memora 上 40%）。FactConsolidation 为纯召回，无法区分控制平面能力。
6. **成本与延迟**：变异时钩子每次 2.3s、$0.17/385 例，确定性延迟 64-191 ms；召回路径不受影响。
7. **通过带**：确定性系统在 385 例上收敛于 63-68%，但外部子集降至 28-51%，说明该区间是经验性饱和而非上限。

## 7. 优点

- **原研性**：首次系统研究 LLM 在记忆流水线中放置位置对遗忘能力的影响，填补控制平面评估空白。
- **完整基准**：ForgetEval 提供 5 族 10 类攻击，手工+LLM 起草结合，多轮验证（IAA、跨族裁判、外部子集），方法论严谨。
- **Adapter 协议**：N/A 评分允许不同系统（有无删除原语）公平比较，降低参与门槛（~130 行 Python），推动社区贡献。
- **广泛对比**：13 种主流开源系统（含 Lethe, MEM0, LangGraph, A-MEM, Graphiti, HippoRAG 等）在同一协议下评估，结论可复现。
- **消融充分**：嵌入器、LLM 模型、架构后端、放置位置等维度均做消除，结论稳健。
- **开源与可复现**：所有基准、适配器、数据、评分脚本均以 MIT 许可证发布，支持单命令复现全部表格和图表。

## 8. 不足与局限

- **英语中心与脚本采样薄**：手工案例全英文；跨语言标识符在 9 种书写系统上采样不均（如拉丁 12 例、希腊 7 例、天城文/泰文仅 1-3 例），无法区分 LLM 钩子系统间差异。
- **系统覆盖有限**：未实测 Zep CE（已弃用）、Cognee（API 不兼容）、Redis Semantic Memory、AutoGen Memory 等；HippoRAG 和 Graphiti 因原语缺失得分极低，但可能是设计目标不同所致。
- **LLM 钩子敏感于模型**：使用 DeepSeek-V3 获得 23-30 pt 提升，但 Qwen-2.5-72B 仅 13 pt，Llama-3.1-70B 无法解析 JSON 合同。更弱模型或特定场景下效果可能大幅下降。
- **compound_fact 为原语存在测试**：该类别测试部分编辑原语，缺乏此原语的系统必然得 0/40，不能反映遗忘能力差异。保留作为诊断，但需注意不混淆。
- **循环性风险**：253/385 对抗案例由 DeepSeek-V3 起草并经 Qwen-2.5-72B 裁判接纳，而 LLM 钩子也使用 DeepSeek-V3。虽通过手工核心和外部子集缓解，但无法完全排除 inductive bias 重叠。外部子集中部分类别全系统失败（如否定陷阱 0/8），暴露基准构造陷阱。
- **评估带宽**：确定性系统在 385 例上重叠区间（63-68%）可能表示基准难度均匀而非系统间无差异；外部子集显示难以程度可变化，因此该带不是绝对上限。
- **缺乏全栈生产级验证**：未在真实企业 CRM 或代理工具上验证 ForgetEval 分数与实际泄露之间的相关性；结构映射（附录 S）为初步，非实证。

## 9. 展望与开放问题

- **基准的演进**：需引入动态遗忘命令（如“删除前天下午的对话”）、跨会话因果推理、以及用户意图模糊的遗忘请求（如“忘记关于X的事”但有歧义）。当前模板多采用明确陈述，缺乏自然语言模糊性。
- **LLM 放置的泛化**：变异时钩子在更强 LLM（DeepSeek-V3, GPT-4）上有效，但在弱模型上可能退化。未来可研究蒸馏或专用小模型（如 7B 参数）的遗忘规划能力。此外，不同 LLM 的 JSON 遵循能力变异时钩子的提升幅度，提示需设计结构化输出约束（如函数调用）来稳定提升。
- **实际部署验证**：将 ForgetEval 应用于真实 CRM 或聊天机器人，测量遗忘失败导致的安全事件（如密码泄露）与实际分数的相关性，以验证基准的生态效度。论文中的结构映射（附录 S）已提供初步对应，但缺乏定量关联分析。
- **与遗忘法规的桥接**：GDPR“被遗忘权”要求彻底删除，而当前的清除原语仅隐藏；未来需结合取证移除与遗忘证明。同时，法律法规中的“合理遗忘”需求（如保留期限届满后自动删除）尚未在当前基准中建模。
- **联合优化**：当前召回-遗忘折中仅在一个示例中展示，未来可在多目标优化框架下同时最大化召回和遗忘得分。现有的非支配点（Lethe 遗忘强、LangGraph 召回强）提示可设计自适应放置策略，根据任务动态切换 LLM 参与位置。
- **对抗案例的自动化生成与验证**：当前手工+LLM 起草流程昂贵且存在循环偏差。未来可建立生成-验证闭环：使用强 LLM（如 GPT-4）生成候选，再由预言（oracle）自动检验，减少人工标注成本。同时，需破解否定陷阱、复合事实等全系统失败的类别，避免基准构造偏误。
- **多模态与流式场景**：当前仅处理文本存储。随着多模态记忆（图像、语音、结构化表格）的兴起，需扩展遗忘原语至多模态表示（如嵌入-字面联合覆盖）、跨模态标识符冲突（如照片中的人脸与文本中的姓名不一致）等故障模式。
- **动态遗忘时间线**：生产系统中遗忘命令通常异步发生（如用户定期清理），而当前基准序列化处理。未来可评测系统在连续遗忘注入下的稳定性（如链式取代导致的级联失效）。

作者已宣布将在 2026 年 Q3 发布 ForgetEval v2 版本，涵盖多语言均匀采样（每书写系统至少 30 例）、全栈生产级验证（企业知识库模拟）、以及轻量级变异时钩子（基于 8B 模型的函数调用）的原型。届时将提供更全面的遗忘能力评估框架。
