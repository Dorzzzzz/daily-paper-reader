## 摘要
多轮LLM智能体将简短查询扩展为长轨迹，包含工具调用、搜索结果和中间推理。在单条轨迹中，KV内存和KV读取带宽均增长数个数量级，使得键值（KV）缓存而非参数计算成为长时域智能体的主要服务瓶颈。我们提出IntentKV，一种在保持基础LLM冻结的情况下进行学习型KV剪枝的方法。IntentKV维护一个跨轮次意图的会话级QueryMemory，通过记忆-注意力规则对活历史令牌评分，并添加一个零初始化的残差头，该残差头对当前查询的K向量进行交叉注意力。为了与前缀缓存保持可组合性，驱逐采用槽位映射重定向：被丢弃的位置路由到一个哨兵死槽位，而存活的K/V行、RoPE相位和槽位身份保持不变。在严格的KV预算下，IntentKV几乎无精度损失地匹配无剪枝全缓存基线：在8k KV预算下，Qwen3-8B的平均峰值请求令牌下降23.9%，Qwen2.5-14B下降30.7%。在Qwen2.5-14B上所有方法都能完成的100个最长BCP查询中，IntentKV-8k进一步将最坏情况峰值请求令牌从92.3k降低到20.5k（减少77.8%），最坏情况原始KV读取从4.11亿降低到3100万（减少92.6%）。

## Abstract
Multi-turn LLM agents fan short queries into long trajectories of tool calls, search results, and intermediate reasoning. Both KV memory and KV read bandwidth grow by orders of magnitude across a single trajectory, making the key-value (KV) cache, not parameter compute, the dominant serving bottleneck for long-horizon agents. We introduce IntentKV, learned KV pruning that keeps the base LLM frozen. IntentKV maintains a session-level QueryMemory of cross-turn intent, scores live history tokens with a memory-attention rule, and adds a zero-initialized residual head with cross-attention over current-query K-vectors. To stay composable with prefix caches, eviction is a slot-map redirection: dropped positions route to a sentinel dead slot while surviving K/V rows, RoPE phases, and slot identities stay in place. IntentKV matches the no-pruning full-cache baseline with almost no accuracy drop under tight KV budgets: at an 8k KV budget, mean peak request tokens drop 23.9% on Qwen3-8B and 30.7% on Qwen2.5-14B. On the 100 longest BCP queries that all methods complete on Qwen2.5-14B, IntentKV-8k further cuts worst-case peak request tokens from 92.3k to 20.5k, a 77.8% reduction, and worst-case raw KV reads from 411M to 31M, a 92.6% reduction.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：多轮大语言模型（LLM）智能体（如浏览、深度研究、工具调用）在单条轨迹中，用户简短查询会膨胀为长序列（工具调用、搜索结果、中间推理），导致键值（KV）缓存内存和读取带宽激增，成为服务瓶颈，而非参数计算。
- **研究动机**：现有KV缓存剪枝方法（如StreamingLLM、SnapKV、H2O）主要针对单次提示压缩，不适用于多轮智能体场景：令牌重要性会跨轮次变化，且剪枝后常用的重定位（compaction）会破坏跨轮次前缀缓存复用（radix prefix cache）。
- **整体含义**：需要一种既能在跨轮次中动态跟踪意图、又能在不重定位存活KV行的情况下进行剪枝的方法，以兼容高效服务系统（如SGLang、vLLM）的缓存复用。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想
- **分离“保留策略”与“布局策略”**：保留策略应追踪会话级别跨轮次意图；布局策略在不移动存活KV行的情况下实现驱逐，从而保持前缀缓存身份。
- **实现方案**：IntentKV包含三个组件：
  1. 会话级QueryMemory，聚合跨轮次查询信号；
  2. 零初始化残差头，基于冻结模型特征学习修正信号；
  3. 槽位映射驱逐（slot-map eviction），将丢弃位置重定向到哨兵死槽，保持存活行位置不变。

### 2.2 关键技术细节
- **QueryMemory更新**：每个会话维护一个形状为L×Hq×D的查询记忆Mt，通过几何递推更新：  
  Mt = e⁻λ·Mt₋₁ + Enc(qt)，其中Enc(qt)平均当前查询区间（actionable query span）的所有后RoPE Q行，λ=0.5固定。更新后对Mt按头维度进行单位范数投影。
- **规则得分（Phase-1）**：对候选历史位置j，计算交叉注意力得分：s_rule(j) = Σₗₕ aₗₕⱼ，其中a类似softmax，使用Mt和K[j]的点击。
- **残差学习（Phase-2）**：最终得分 s(j) = s_rule(j) + α·MLP([φⱼ, cⱼ])，其中φⱼ包括平均K向量、平均记忆向量、元素积、规则得分；cⱼ通过交叉注意力从当前查询的K向量中读出。MLP输出零初始化，α初始为1，确保开始时完全恢复规则得分。仅214,274个可训练参数。
- **驱逐方式**：不进行压缩（compaction），而是修改槽位映射Sr：被丢弃位置指向一个哨兵死槽（s†），其K=-10⁴、V=0。保留所有存活的K/V行、RoPE相位和逻辑槽位。前缀缓存仍然有效。死槽在注意力中由于极低softmax权重和零值贡献等效于硬掩码。
- **释放检查**：回收到物理槽位前需满足三个条件（不在前缀保护范围内、不是哨兵、不在存活集合中），避免别名冲突。

- **准确性**：在C=8k严格预算下，IntentKV-Phase-2在Qwen3-8B上达到14.10 True Acc（完整缓存16.92），优于最强基线StreamingLLM（11.81）；在Qwen2.5-14B上达到18.55（完整缓存20.60），远超StreamingLLM（8.19）。C=16k时IntentKV几乎匹配完整缓存。
- **效率**：壁钟时间节省高达43-46%，原始KV读取减少高达59-93%（与紧凑基线相比）；在最坏情况（100个最长查询）下，峰值请求令牌降低77.8%，原始KV读取降低92.6%。
- **前缀重用**：死槽布局使前缀命中率保持在20.7%（C=8k）和26.0%（C=16k），而紧凑基线下降到0-3%。

- **TrimKV对比**：IntentKV在完成率上显著超越TrimKV（84.58% vs 51.57%），真实准确率领先3.14点，归因于QueryMemory更适应工具调用任务（有用令牌往往较旧）。

  - 死槽驱逐布局保留前缀缓存身份，使剪枝与系统级缓存复用兼容，现有baseline直接受益。

## 8. 不足与局限

- **预算固定**：当前使用全局统一预算C，无法根据轨迹动态调整。短查询承受不必要的驱逐开销，极长查询（92-115k令牌尾）被迫与中位数查询经历相同压缩曲线。未来工作可探索自适应预算选择。
- **监督与领域限制**：Phase-2残差仅在ToolBench上训练，使用未来工具调用参数的字面子串匹配标签，泛化到非代理工作负载或单轮输入时增益可能较小（但规则得分提供保护）。
- **模型覆盖有限**：仅验证Qwen3-8B和Qwen2.5-14B。其他主流开源骨干（Llama-3.1、Mistral、GLM-4等）因无法在BCP上自主多轮工具调用而无法参与KV压缩比较，因此无法完全证明方法对任意骨干的泛化性。≥70B模型未测试。
- **硬件要求**：死槽哨兵需要fp16/bf16 KV池，可能限制某些部署环境。
- **实验客观性讨论**：
  - 所有基线均使用作者实现的意图，但在标准服务配置下运行（压缩基线禁用前缀重用以避免RoPE错误，IntentKV启用）。布局消融（表7）证明死槽布局本身带来部分优势，但论文也承认布局和评分相互正交。

  - 整体实验设计公平：统一解码、裁判、检索缓存，预算定义一致（仅压缩可压缩历史，而非全长）。
- **应用限制**：方法依赖于会话ID的确定（需显式session_id或哈希），多租户环境下需LRU缓存管理。
