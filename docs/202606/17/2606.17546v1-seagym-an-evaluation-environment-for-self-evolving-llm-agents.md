## 摘要
自进化基于LLM的智能体主要通过改变其智能体框架来改进：基座模型周围的结构化执行层，包括提示、记忆、工具、中间件、运行时状态以及模型-工具交互循环。现有的评估常常将此过程简化为孤立的任务分数或单一的顺序曲线，掩盖了更新是否产生了可重复利用的改进、过度拟合近期任务、增加成本或损害旧行为。我们引入了SEAGym，一个用于衡量智能体框架更新在训练、验证、测试、重放和成本记录上的评估环境。SEAGym将兼容Harbor的基准测试转化为动态自进化任务源，包含训练批次、冻结更新验证、保留的ID和OOD迁移视图、重放诊断以及保存的快照和指标记录。在Terminal-Bench 2.0和HLE上实例化SEAGym，我们在共享的epoch/batch协议下比较了ACE、TF-GRPO和AHE。结果表明，这些评估视图提供了关于进化过程的互补信号：频繁更新可能无法提高保留性能，有用的中间快照可能后来崩溃，源多样性和模型后端可能影响框架的可靠性。

## Abstract
Self-evolving LLM-based agents improve mainly by changing their agent harness: the structured execution layer around a base model, including prompts, memory, tools, middleware, runtime state, and the model-tool interaction loop. Existing evaluations often reduce this process to isolated task scores or a single sequential curve, obscuring whether an update produces reusable improvement, overfits recent tasks, increases cost, or harms older behavior. We introduce SEAGym, an evaluation environment for measuring agent harness updates across training, validation, test, replay, and cost records. SEAGym turns Harbor-compatible benchmarks into dynamic self-evolution task sources with train batches, frozen update-validation, held-out ID and OOD transfer views, replay diagnostics, and saved snapshot and metric records. Instantiating SEAGym on Terminal-Bench 2.0 and HLE, we compare ACE, TF-GRPO, and AHE under a shared epoch/batch protocol. The results show that these evaluation views provide complementary signals about the evolution process: frequent updates may fail to improve held-out performance, useful intermediate snapshots may collapse later, and source diversity and model backend can affect harness reliability.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：现有评估将自进化LLM智能体的改进过程简化为孤立任务分数或单一顺序曲线，无法回答关键问题——更新是否产生可复用改进、是否过拟合近期任务、是否增加成本、是否损害旧行为。
- **背景**：智能体框架（agent harness）包括提示、记忆、工具、中间件、运行时状态等结构层，是自进化的主要修改对象。但现有基准（如SWE-bench、WebArena）采用静态评估，每次任务重置状态；少数序列/终身评估（如SEA-Eval）也未能覆盖单任务自适应、epoch级学习等常见设置。
- **动机**：需要统一评估环境，显式分离训练、验证、测试、重放和成本记录，以揭示不同自进化方法在更新过程中的具体行为、泛化性和稳定性。

## 2. 方法论

### 核心思想
- 将自进化过程建模为**MDP风格评估过程** \(M = (S, A, P, R, \rho)\)，其中状态 \(s_t\) 包含当前智能体快照（固定基模型 \(M\) + 可变框架状态 \(H_t\)）、调度位置和任务上下文。
- 环境负责采样任务批次、提供反馈，智能体负责执行策略和更新规则 \(H_{t+1} = U(H_t, B_t, T_t, F_t)\)。
- SEAGym 提供**可配置调度参数**（状态持久性、任务复用、批大小、更新重复、评估时机），统一支持在线、单任务、批量、epoch级进化设置。

### 关键技术细节
- **数据划分与评估视图**：
  - 基础分割：\(D_{\text{train}}, D_{\text{val}}, D_{\text{test}}\) 控制任务可见性和更新证据。
  - 评估视图：更新验证（update-validation）、保留ID迁移、OOD迁移、重放/保留诊断。
  - 禁止将验证集或测试集证据混入更新，确保评估纯净。
- **基准集成**：
  - 复用Harbor作为任务运行后端（任务定义、环境、验证器、并行执行）。
  - 提供 `rollout`/`update` 接口，分离轨迹收集与框架更新，各方法保持原生更新语义。
- **指标**：
  - 主要：Perf（平均得分）、SR（成功率）、UVG（更新验证增益）、IDG/OODG（迁移增益）、FR（遗忘率）。
  - 辅助：token用量、工具调用次数、时间、成本。

### 算法流程（文字说明）
1. 从训练集中采样批次，选定验证/测试/重放视图。
2. 记录初始快照 \(A_0\)。
3. 对每个epoch：
   - 对每个训练批次：执行任务，收集轨迹和反馈；智能体调用更新规则更新框架状态；保存更新摘要。
   - 在每个epoch结束时冻结当前快照，并在更新验证视图上评估。
4. 对初始快照和最终快照进行保留ID、OOD和重放评估。

## 3. 实验设计

### 数据集/场景
- **来源**：Terminal-Bench 2.0（命令行/软件工程任务，容器化执行） + HLE（专家级QA，文本Math/Physics作为源，CS/AI和Engineering作为OOD）。
- **规模**：80个训练任务、35个验证任务、55个ID测试任务，80个OOD测试任务。
- **训练设置**：5个epoch，默认批大小20，每个epoch结束后冻结快照评估。

### 对比方法
- **ACE**：进化持久上下文（技能/策略记忆）——更新技能书，不改执行路径。
- **TF-GRPO**：基于分组轨迹证据更新经验/上下文存储。
- **AHE**：编辑完整框架（提示、中间件、记忆、工具项目文件）——直接改变运行时行为。
- **基模型**：主实验使用DeepSeek-V4-Flash；跨模型实验使用GLM-5.1和GPT-5.4。

### 消融实验
- **批大小消融**：10、20、40、80。
- **源多样性消融**：混合源 vs HLE-only。
- **跨模型迁移**：用不同后端训练的快照在不同后端上评估ID/OOD。

## 6. 主要结论与发现
1. **AHE同时提升验证、ID和OOD**：其框架编辑能力（工具、中间件、验证规则）可改变执行路径，但也会引入中间可靠性风险。
2. **ACE产生适度ID/OOD增益**：技能书提供可复用的过程知识，但无法改变运行时行为，对交互策略失败改进有限。
3. **TF-GRPO产生大验证增益但OOD下降**：分组轨迹证据快速优化源分布表现，但泛化性不足，且展现代价最高。
4. **批大小非单调**：批20最佳（证据多样性、每任务分析深度、更新频率平衡）；太小则局部噪声积累，太大则稀释每任务注意力。
5. **源多样性有助于恢复**：混合源暴露工具/环境/推理多种失败，后期可修复中间崩溃；单源HLE最终快照因中间件消息合约问题崩溃。
6. **跨模型迁移不对称**：同一后端训练的快照在同后端上ID增益明显，但跨后端和OOD表现可能为负，说明框架编辑依赖观察到的失败表面。
7. **中间快照可能崩溃与恢复**：重放诊断显示E16因消息合约错误导致大面积执行错误，最终快照修复后恢复。

## 7. 优点
- **多视图评估设计**：分离更新验证、ID/OOD迁移、重放和成本，提供进化过程的互补信号，避免单一曲线掩盖退化。
- **通用性**：基于Harbor兼容现有基准，定义清晰的rollout/update接口，可接入多种自进化方法。
- **可诊断性**：保存完整快照、轨迹引用、更新摘要，支持离线过程诊断（如合约错误、遗忘模式）。
- **调度参数化**：统一支持在线、单任务、批量、epoch等常见进化设置，避免硬编码。
- **指标全面**：包含遗忘率、成本、token消耗，有助于理解更新效率。

## 8. 不足与局限
- **域覆盖有限**：仅实验了Terminal-Bench和HLE（执行密集型 + 推理密集型），未覆盖web/桌面交互、长周期软件工程、数据分析和多智能体协作。扩展需要新Harbor兼容任务源。
- **只研究模型外框架进化**：未考虑模型权重更新（online RL fine-tuning）或混合系统，未来可扩展。
- **成本/覆盖权衡**：保存多视图快照并重放增加计算开销，未研究自适应快照选择或预算敏感评估。
- **跨模型和OOD实验规模有限**：仅3种后端、1种OOD源（HLE CS/AI+Engineer），可能受特定后端行为影响。
- **hidden verifier artifacts风险**：需避免将验证器细节泄露给智能体，论文已声明限制。
- **基准集成依赖Harbor**：若基准不兼容Harbor则需额外适配工作。
