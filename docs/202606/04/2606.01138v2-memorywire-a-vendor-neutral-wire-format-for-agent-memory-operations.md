## 摘要
智能体记忆框架——mem0、Letta/MemGPT、Cognee、Zep/Graphiti、MemoryOS、MemTensor——各自提供自己的SDK、存储布局和操作词汇。没有共享的线格式：每次集成都是定制的，每次迁移都从头重建记忆，并且没有框架提供治理界面让人类在写入进入长期存储之前进行审查。我们提出memorywire，这是一种基于JSON-Schema 2020-12的线格式，支持四种记忆类型（语义、情景、程序、情感）上的五种记忆操作（记住、回忆、遗忘、合并、过期），并包含MemoryStore接口、扇出路由器和可选的HITL治理通道。我们描述了一个开源参考实现，包含五个后端适配器（sqlite-vec、mem0、Letta、Cognee、pgvector）；在一个包含100个事实/50个查询的标注语料库（42个非空gold id + 8个无匹配探测）上的微基准测试中，在42个gold id查询上实现了recall@5 = 1.000，摄入p50 = 37.8毫秒，回忆p50 = 40.6毫秒；一个对抗性融合实验表明，在1-of-N rank-0注入扫描（K ∈ {0, 5, ..., 50}）中，倒数秩融合（RRF）在整个范围内保持recall@5 = 1.000，而最大融合在K ≥ 5时降至0.500且泄漏80%；以及一个包含16个场景的跨适配器一致性测试套件，80个单元中通过68个，零失败。贡献不在于新算法；而在于将成熟组件（RRF、FSM、STM/LTM巩固、差异与批准工作流）打包成一个与场所无关的协议，并附有经验验证的参考实现，旨在与模型上下文协议（MCP）协作而非竞争。

## Abstract
Agent-memory frameworks -- mem0, Letta/MemGPT, Cognee, Zep/Graphiti, MemoryOS, MemTensor -- each ship their own SDK, storage layout, and operational vocabulary. There is no shared wire format: every integration is bespoke, every migration rebuilds memory from scratch, and no framework ships a governance surface that lets a human review writes before they enter long-term storage. We present memorywire, a JSON-Schema 2020-12 wire format for five memory operations (remember, recall, forget, merge, expire) over four memory types (semantic, episodic, procedural, emotional), with a MemoryStore interface, a fan-out router, and an optional HITL governance channel. We describe an open-source reference implementation with five backend adapters (sqlite-vec, mem0, Letta, Cognee, pgvector); a microbenchmark on a 100-fact / 50-query labelled corpus (42 with non-empty gold ids + 8 no-match probes) achieving recall@5 = 1.000 on the 42 gold-id queries with ingest p50 = 37.8 ms and recall p50 = 40.6 ms; an adversarial-fusion experiment showing Reciprocal Rank Fusion holds recall@5 = 1.000 across a 1-of-N rank-0 injection sweep (K in {0, 5, ..., 50}) where max fusion collapses to 0.500 with 80% leak at K >= 5; and a 16-scenario cross-adapter conformance suite passing 68 of 80 cells with zero failures. The contribution is not a new algorithm; it is a packaging of established components (RRF, FSMs, STM/LTM consolidation, diff-and-approve workflows) into a venue-neutral protocol with an empirically validated reference, positioned to compose with the Model Context Protocol rather than compete with it.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：当前智能体记忆框架（如 mem0、Letta/MemGPT、Cognee、Zep/Graphiti、MemoryOS、MemTensor）各自为政，没有统一的标准线格式（wire format）。每个框架拥有自己独特的 SDK、存储布局和操作词汇，导致跨框架集成需要定制化开发，迁移时记忆需重建，且没有任何框架提供供人类在写入长期存储前进行审核的治理界面（governance surface）。
- **研究动机**：现有框架在操作语义、记忆类型分类、生命周期管理上高度异构，缺乏共享协议；同时，缺少人类参与的记忆写入审批机制（human-in-the-loop，HITL），即“先差异审查后批准”的工作流。
- **整体含义**：memorywire 旨在填补这一空白，它不是提出新算法，而是将已有的成熟组件（如倒数秩融合 RRF、有限状态机 FSM、短期/长期记忆巩固、差异-批准工作流）打包成一个厂商中立、传输无关的协议，使其能够与模型上下文协议（MCP）组合而非竞争，从而降低代理记忆系统的碎片化。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：定义一个基于 JSON-Schema 2020-12 的线格式，标准化四种记忆类型上的五种操作，并包含一个可选的治理通道。
- **记忆类型**：语义（semantic）、情景（episodic）、程序（procedural）、情感（emotional），源自认知科学分类（Tulving, Squire）。
- **操作**：
  - `remember`（写入）：必需字段包括 agent_id、type、content；可选用 user_id、metadata、confidence（[0,1]）、source、expires_at、approval_required。
  - `recall`（读取）：必需 agent_id、query；可选 k、types、hops（图跳数）、fusion（rrf/max/weighted）、filter、fresher_than_days。
  - `forget`（删除）：必需 agent_id 和至少 ids 或 filter（防止无范围批量删除），支持软/硬删除。
  - `merge`（合并）：必需 agent_id、canonical、duplicates；可选 strategy（keep_canonical / merge_content / keep_highest_confidence）。
  - `expire`（过期策略）：必需 agent_id；可选 policy（older_than_days、type、confidence_below、no_recall_in_days）和 action（forget/archive/demote）。
- **MemoryStore 协议**：定义了 `remember`、`recall`、`forget`、`merge`、`expire`、`health` 和 `capabilities`（声明支持的操作与记忆类型）的抽象接口。后端适配器实现该协议，使协议与后端无关。
- **记忆路由器（Memory Router）**：本身也实现 MemoryStore，维护 N 个子存储。对 `remember` 默认向所有子存储扇形写入；对 `recall` 向所有子存储并行查询并融合结果；对 `forget`/`merge`/`expire` 汇总各存储结果和错误。
- **融合算法**：
  - RRF（默认）：`score(d) = Σ_{i in S} 1/(k + r_i(d))`，其中 k=60，仅依赖排名，不依赖原始分数。
  - MAX：取所有存储中该条目的最高原始分数。
  - WEIGHTED：加权和，权重可配置。
- **图跳数提升**：当 `hops > 0` 且至少一个存储声明 `graph` 能力时，对融合结果中邻居也在结果集中的条目施乘性提升：`final(d) = rrf(d) * (1 + 0.1/(1 + hop_dist(d)))`。
- **部分失败模型**：使用 `asyncio.gather(..., return_exceptions=True)`，单个存储超时或失败不会使整个操作崩溃，路由器继续使用存活的存储结果。
- **治理通道**：当 `approval_required=True` 时，`remember`/`forget`/`merge` 操作先通过治理 UI 暂存（`deleted_at = -1` 哨兵），等待人工审批或拒绝。治理 UI 还包含审批学习循环（自动允许高频批准的 pattern）。
- **STMLTM 转换器**：后台异步任务，按间隔（默认 60 秒）评分短期记忆（最近 N 项）的及时性、提及频率和置信度，将高分项提升为长期记忆（类型=semantic），并移除冷项。

## 3. 实验设计：数据集、基准、对比方法

- **微基准测试（Microbenchmark）**：
  - 数据集：100 个手写事实，涉及约 10 个不同用户，混合四种记忆类型。50 个手写查询（42 个含非空 gold id + 8 个无匹配探测），包括 24 个改写查询、10 个精确/近精确匹配、8 个多命中查询、8 个无匹配探测。
  - 嵌入器：`sentence-transformers/all-MiniLM-L6-v2`（384 维，CPU）。
  - 后端：单个 `SqliteVecStore(":memory:")`，内部 RRF 融合（vec0 ANN + FTS5 关键词搜索）。
  - 指标：Recall@5、Precision@5、摄入和回忆延迟（p50/p95/p99）、无匹配探测是否正确为空。
- **对抗性融合实验**：
  - 场景：三个子存储（2 个良性 + 1 个恶意）。恶意存储返回 K 个攻击者控制 ID（disjoint from gold）在 rank 0~K-1。查询套件 20 个，每个有 2 个 gold ID，来自 50 个合成的语料库。K ∈ {0,5,...,50}。
  - 对比融合算法：RRF、MAX、WEIGHTED（等权重）。
  - 指标：recall@5、攻击者泄漏率（返回 ID 中 attacker-controlled 比例）。
- **跨适配器一致性测试（Conformance Suite）**：
  - 16 个协议不变场景，对所有 5 个适配器（sqlite-vec, mem0, Letta, Cognee, pgvector）执行。
  - 结果矩阵：80 个单元格（16 场景 ×5 适配器），记录通过/跳过/失败。
  - 跳过的场景被分类并分析原因（如缺少 user_id 命名空间、无空政策保护、无稳定 ID）。
- **初步 LongMemEval 和 LoCoMo 评估**：
  - 使用 `gpt-4o-mini` 作为评判，`all-MiniLM-L6-v2` 嵌入器，sqlite-vec 后端。LongMemEval 12 个问题、LoCoMo 10 个问题，1 个种子。
  - 报告修复前后的分数对比。

## 6. 论文的主要结论与发现

- **主要结论**：
  1. 微基准测试中，单后端内部 RRF 融合实现了 recall@5 = 1.000（42 个 gold id 查询），摄入 p50=37.8ms，回忆 p50=40.6ms。无匹配探测未被正确忽略（0/8），因为 v0 未实现校准的相关性阈值，这是已知限制。
  2. 对抗性融合实验中，RRF 在整个 K 扫描中保持 recall@5=1.000、泄漏 0%；而 MAX 在 K=5 时召回降至 0.500、泄漏 80%。WEIGHTED（等权）结果与 RRF 相同。
  3. 跨适配器一致性测试：68/80 通过，12 跳过（因适配器自身限制），0 失败。跳过的单元暴露了 spec 中三个规格收紧信号：缺少 user_id 支持、无空政策守卫、缺乏稳定 per-record ID。
  4. 初步 LongMemEval/LoCoMo 结果（修复后）有提升，但样本数少，仅作为进展参考。
- **整体发现**：memorywire 协议是可行的，能够桥接现有框架异质性；RRF 在融合中提供对恶意后端的鲁棒性；一致性测试表明协议中立性实现。

## 7. 优点

- **协议设计**：小而精的操作集合（5 个）和类型集合（4 个），平衡了表达力和简洁性。基于 JSON-Schema 2020-12，便于跨语言代码生成。
- **异构兼容性**：通过 `capabilities` 声明和部分失败模型，路由器能同时操作不同能力和可靠性的后端，且单后端故障不影响整体。
- **安全与治理**：内置可选 HITL 治理通道，且规范了差异-批准流程；对抗融合实验定量证明了 RRF 在恶意后端威胁下的优越性。
- **一致性测试**：16 场景跨适配器测试能直接暴露规格漏洞，有助于协议迭代。
- **开放与复现**：所有实验脚本、数据集、结果 JSON 文件全部开源；Apache-2.0 许可证，便于集成。
- **与 MCP 的互补关系**：明确说明了三种组合模式，不与 MCP 竞争，而是填补了 MCP 未涉及的记忆领域。

## 8. 不足与局限

- **实验覆盖**：
  - 微基准语料太小（100 事实），无法代表百万级真实工作负载。
  - 对抗实验假设攻击者拥有完全知识（知道路由器 over-fetch 量），实际操作中黑盒攻击效果更弱，但未评估更复杂的攻击如伪造出现在良性存储结果中的 ID。
  - 所有实验在单机 CPU 上运行，缺少分布式、网络 RTT、多线程扇出等真实因素。
  - 初步基准样本量极小（n=10-12, nseed=1），无法支持统计结论；且使用弱嵌入器 `all-MiniLM-L6-v2`，protocol 本身是嵌入器无关但实验仅反映该嵌入器的天花板。
- **协议成熟度**：
  - v0 版本允许向后不兼容变更至 v0.5，目前非稳定标准。
  - 缺乏对 `recall` 操作的治理（仅审计日志）、无召回预算限制、无字段级别红action。
  - 空过期政策默认无错误（仅 SQL 后端有保护），可能导致意外删除所有条目。
- **实现上的限制**：
  - 部分后端（如 mem0、Letta、Cognee）因自身 API 限制无法完整支持 memorywire 规范：缺少 user_id 命名空间、缺少稳定记录 ID，导致一些操作（如按 ID 删除）被跳过。
- **评价偏见**：作者同时是评估者，无第三方审计。用户研究计划在 v0.2。
- **其他**：未进行与现有框架的直接系统级比较（例如让多个框架运行相同基准并对比代价/功能），因此虽然协议可行，但未量化它带来的实际迁移或集成成本节省。
