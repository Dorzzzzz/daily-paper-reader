## 摘要
LLM代理会积累超出其上下文窗口的历史记录，这推动了关于记忆系统的研究日益增多。然而，现有大多数设计都针对单一场景（多轮对话或单条轨迹格式）进行调优，几乎没有证据表明它们能够泛化到代理在部署中遇到的异构轨迹。我们重新审视了八个记忆系统以及一个用于搜索问题的智能体框架，在五个场景上进行了测试：单轮问答、多轮对话、智能体轨迹问答、记忆压力测试和长周期智能体任务。该框架通过工具调用自行管理平面文本文件存储，取得了最佳的跨任务排名，这表明记忆性能的关键在于赋予代理对存储和检索的主动控制，而非固定管道背后的被动存储。我们将这一见解实例化为AutoMEM，这是一个具有自管理工具接口的智能体记忆框架，在我们评估的系统中实现了最佳的跨场景泛化能力。

## Abstract
LLM agents accumulate histories that outgrow their context windows, motivating a growing literature on memory systems. Yet most existing designs are tuned to a single scenario (multi-session chat or a single trajectory format), and there is little evidence that they generalize across the heterogeneous trajectories agents encounter in deployment. We revisit eight memory systems plus an agentic harness for search problems, on five scenarios: single-turn QA, multi-session chat, agentic-trajectory QA, memory stress tests, and long-horizon agentic tasks. The harness, which self-manages flat text-file storage via tool calls, achieves the best cross-task ranking, suggesting that memory performance hinges on giving the agent active control over storage and retrieval rather than on a passive store behind a fixed pipeline. We instantiate this insight in AutoMEM, an agentic memory harness with a self-managed tool interface that achieves the best cross-scenario generality among the systems we evaluate.

- **整体含义**：记忆系统的泛化性不仅关乎准确性，还与**部署成本（token 成本、延迟）** 密切相关；仅依赖固定管线的被动存储不足以支撑真实世界的多变代理任务，**主动控制**（agentic harness）才是关键。

## 2. 方法论：核心思想、关键技术细节、算法流程

### 核心思想
- **记忆性能取决于赋予代理对存储和检索的主动控制**，而非固定管线后的被动存储。作者将此观点实例化为 **AutoMEM**：一种智能体记忆框架，通过**工具调用接口**使 LLM 在查询时自主决定如何检索和组合证据，将模式承诺从构建时推迟到查询时，从而提升跨场景泛化。

### 关键技术细节
- **存储**：与 LightMem（或可选 PlugMem）结合，预构建一个轻量级索引（如 Cypher 图，包含 SAID_BY、OF_TOPIC、FOLLOWS 等关系），但核心策略是保持原始轨迹为扁平文本文件（raw text），仅通过工具接口访问。
- **检索过程（算法 1：AutoMEM agentic memory-access loop）**：
    1. **规划**：LLM 从动作集合 \( \mathcal{A} = \{\text{rg, read, dump, index\_query}\} \) 中选择一个动作（如正则匹配、按 ID 读取、转储短文本、索引查询）；
    2. **执行**：调用所选工具，返回证据，并追加到运行轨迹（trace）；
    3. **判断**：一个 LLM 法官检查轨迹是否足够；若不足，返回提示缺少什么，并重新调用规划器；
    4. **回答**：当法官认为充分时，LLM 答案器组合最终答案。
- **优化**：采用 KV-cache 友好的聊天布局（系统消息固定，用户消息放目录和图模式提示），将前缀缓存命中率从 5.4% 提升至 50%+；同时提供单遍（single-pass）变体（跳过法官–重规划步骤），以较小精度损失换取大幅降低的 token 成本。

### 算法流程（文字描述）
1. 初始化空证据轨迹和法官提示。
2. 循环至多 \( K_{\max} \) 步：
   - 规划器 LLM 调用，输出一个动作（rg / read / dump / index_query）。
   - 执行器工具调用（无 LLM），获取证据。
   - 法官 LLM 判断证据是否充分；若足够则跳出，否则更新提示。
3. 答案器 LLM 基于最终轨迹生成答案。

## 6. 主要结论与发现

1. **没有单一方法在所有场景中占优**，但 DCI-Lite（agent harness）取得了最佳的跨场景排名（平均分数排名 3.67，最低）。索引型方法在代理轨迹 QA 上显著落后。
2. **索引型方法在代理轨迹上存在两种失败模式**：
   - **表示级失败**：构建时模式会丢弃步骤索引和动作标签（如 HippoRAG 的实体关系 KG 无法编码步骤信息）。
   - **检索级失败**：被动检索无法从仍保留信息的存储中面出证据（如 PlugMem 的原始轨迹仍存储但路由器选错分支）。
3. **主动控制优于被动存储**：DCI-Lite 通过将模式承诺推迟到查询时，实现泛化；AutoMEM 进一步结合选择性索引，在 LoCoMo 上比 DCI-Lite 提升 49.6%，整体排名比 DCI-Lite 提高 24.4%。
4. **长上下文基线比普遍认为的更强且成本具有竞争力**，在许多场景下胜过索引方法。
5. **动态代理任务（如 ALFWorld）上，记忆设计的影响有限**，性能瓶颈更多来自代理的策略（后训练 RL 才能进一步改善）。
6. **索引方法只有满足两个条件时才值得**：工作负载能均摊构建成本（N 足够大）且结构率足够高来奖励聚合；同时模式必须足够表达力。

## 7. 优点

- **全面的跨场景评估**：覆盖单轮 QA、多轮对话、代理轨迹 QA、压力测试、真实代理任务，并同时跟踪 token 成本和延迟，填补了以往只关注单场景的空白。
- **诊断深入**：通过 oracle 存储可回答性、受控探针、结构率分析等手段，将索引方法的失败定位到表示级和检索级两个具体环节，揭示了“主动控制”为何关键。
- **提出实用系统 AutoMEM**：算法设计清晰（规划-执行-判断-回答循环），并附带工程优化（KV-cache 友好布局、单遍快速变体），在保持泛化优势的同时兼顾效率。
- **结论可信度高**：在两种骨干模型（32B 和 4B）上验证，确认趋势一致；报告了方差和多种成本度量；提供了开源代码仓库（通过 HuggingFace 发布制品）。
- **诚实指出局限性**：没有实现分层预算路由（统一骨干导致成本高估）、判定提示的变化可能影响绝对排名等。

## 8. 不足与局限

- **实验覆盖方面的局限**：
  - 未评估所有可能的记忆设计（如 OS 层内存分页、更复杂的 RL 策略等），选择的方法可能未完全覆盖整个设计空间。
  - 所有实验基于固定的基准子集（如 HotpotQA 200 问题），可能无法完全代表完整数据集的难度分布。
  - 动态代理任务（MemoryArena、ALFWorld）的样本量较小（各 30–60 任务），可能导致方差较大。
- **偏差风险**：
  - 使用 LLM 法官作为主要指标，尽管进行了严格的事实判定，但绝对评分可能受判定提示影响，相对排序在其他判定协议下可能变化（作者已提及）。
  - 所有骨干模型固定为 Qwen3 系列，结果可能不直接迁移到其他 LLM（如 GPT-4、Claude）。
- **应用限制**：
  - AutoMEM 在设计上假设存储包含用户数据时需要访问控制、内容过滤等安全机制，论文未涉及。
  - 单遍快速变体在结构率低的场景下可能损失准确性；全循环的 token 开销在极低成本要求下仍可能过高。
- **其他**：
  - 没有实现分层预算路由（将规划和判断交给廉价模型），导致 AutoMEM 的 token 成本报告为上限。
  - “成本-准确率”权衡的帕累托边界仅基于现有方法，未探索更优化的组合如轻量索引 + 主动检索 + 分层路由。
  - 对于动态代理任务（ALFWorld），实验显示记忆无法超越策略限制，但原因分析（Gap 2：状态依赖决策）仅基于少量失败案例，可能不够全面。
