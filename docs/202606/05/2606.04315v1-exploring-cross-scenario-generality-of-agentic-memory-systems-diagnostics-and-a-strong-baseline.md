## 摘要
LLM智能体积累的历史会超出其上下文窗口，这推动了对记忆系统的研究日益增多。然而，现有大多数设计仅针对单一场景（多会话聊天或单一轨迹格式）进行调优，几乎没有证据表明它们能够泛化到部署中智能体遇到的各种异构轨迹。我们重新审视了八个记忆系统以及一个用于搜索问题的智能体框架，在五个场景上进行了评估：单轮问答、多会话聊天、智能体轨迹问答、记忆压力测试以及长期智能体任务。该框架通过工具调用自主管理纯文本文件存储，在跨任务排名中表现最佳，这表明记忆性能的关键在于赋予智能体对存储和检索的主动控制权，而不是在固定流水线后设置被动存储。我们将这一见解实例化为AutoMEM，一个具有自主管理工具接口的智能体记忆框架，在我们评估的系统中实现了最佳的跨场景通用性。

## Abstract
LLM agents accumulate histories that outgrow their context windows, motivating a growing literature on memory systems. Yet most existing designs are tuned to a single scenario (multi-session chat or a single trajectory format), and there is little evidence that they generalize across the heterogeneous trajectories agents encounter in deployment. We revisit eight memory systems plus an agentic harness for search problems, on five scenarios: single-turn QA, multi-session chat, agentic-trajectory QA, memory stress tests, and long-horizon agentic tasks. The harness, which self-manages flat text-file storage via tool calls, achieves the best cross-task ranking, suggesting that memory performance hinges on giving the agent active control over storage and retrieval rather than on a passive store behind a fixed pipeline. We instantiate this insight in AutoMEM, an agentic memory harness with a self-managed tool interface that achieves the best cross-scenario generality among the systems we evaluate.

## 论文提出的方法论
### 核心思想
记忆性能的关键在于**赋予智能体对存储和检索的主动控制权**，而非依赖固定流水线后的被动存储（如预先构建的索引）。基于此，作者提出了一个智能体记忆框架 **AutoMEM**，它通过一个自管理的工具接口让LLM在运行时自主决定如何检索和组合所需信息。

### 关键技术细节
- **Agent Harness（基础方案）**：将历史轨迹以纯文本文件形式存储，让LLM使用`grep`、`read`等工具自行检索，不预先构建结构化索引。这一设计在跨场景排名中领先。
- **AutoMEM算法**（Algorithm 1）：
  - 一个多步骤的“规划-执行-判断”循环。
  - 每个步骤，智能体从四个动作菜单中选择一个：`rg`（正则搜索原始记录）、`read`（按ID读取记录）、`dump`（将短文本直接送给答案LLM）、`index_query`（对预构建索引进行类型化查询）。
  - 规划器LLM编写调用，执行器运行，证据追加到运行轨迹。
  - 一个LLM裁判检查轨迹是否足够；若不足，裁判返回缺失线索，规划器重新调用；若充足，构成最终答案。
  - 默认索引使用Cypher图（基于LightMem的摘要索引），包含边类型`SAID_BY`, `OF_TOPIC`, `FOLLOWS`；也可换成PlugMem图。
- **进一步效率优化**：
  - KV缓存友好的聊天布局：将稳定指令块放在系统消息，用户消息放置语料目录和图模式提示，提升前缀缓存命中率。
  - 单次传递变体（single-pass）：固定`Kmax=1`，禁止`dump`分支，跳过裁判-重规划步骤，一次并行执行`rg`、`read`、`index_query`，以小幅精度损失换取大幅减少查询令牌（66–72%）。

### 算法流程（文字描述）
```
1. 初始化证据轨迹trace为空，反馈提示hint为空。
2. 对于k=1到最大步数：
   a. 规划器根据问题、当前trace和hint选择一个动作。
   b. 执行器在存储上运行该动作，得到输出。
   c. 将动作和输出追加到trace。
   d. 裁判检查trace是否足以回答问题；若足够，跳出循环；否则设置hint为缺失理由。
3. 答案生成器基于trace和问题生成最终答案。
```

## 主要结论与发现
1. **没有方法在所有场景占优**：每种预构建索引的方法至少在一个基准上落后于长上下文。DCI-Lite（agent harness）取得最佳通用性排名。
2. **索引式方法在智能体轨迹QA上出现两种失效模式**：
   - **表征级失效**：构建时模式（如实体-关系KG）丢弃了步骤索引和动作标签，数据在检索前即丢失。
   - **检索级失效**：即使存储保留了证据，被动检索（如路由选择、语义搜索）无法可靠地将其提取出来，因为检索接口不能根据问题动态调整。
3. **主动控制优于被动管道**：允许智能体在查询时决定如何检索（如grep/read）比预构建索引更具跨场景泛化能力。
4. **索引仍有价值，但条件严格**：只有当工作负载具有高结构率（即需要跨单元聚合的查询占比大）且索引模式能编码所需谓词时，索引才值得构建成本。
5. **动态智能体任务受限于策略而非记忆**：即使在ALFWorld上使用完美的过程记忆，仍有部分失败源于状态关联决策，需参数更新（如RL）才能突破。
6. **AutoMEM设计有效**：结合agent harness与选择性索引，在LoCoMo上比DCI-Lite提升22.3个百分点，比长上下文提升5.8个百分点；整体平均排名3.10（优于DCI-Lite的4.10）。

## 优点
1. **跨场景视角新颖**：首次系统评估记忆系统在五个异构场景上的泛化性，弥补了以往单一场景评估的不足。
2. **诊断深入**：通过Oracle存储可回答性、结构率分析等实验精确定位索引方法的失效根源，而非简单报告性能差距。
3. **方法论简洁有效**：AutoMEM的设计基于观察到的两个失效模式，通过让智能体主动控制检索，既保持泛化性又能利用索引优势，实现高效的折中。
4. **评估全面**：不仅跟踪准确率，还系统比较了令牌成本和延迟（包括实时指标如前缀缓存命中率、解码MFU），揭示令牌计数不能反映实际成本。

## 不足与局限
1. **未实现分层预算路由**：AutoMEM对所有步骤（规划、裁判、答案生成）使用同一大型模型，未能根据任务难度选择更便宜的模型，导致成本为上限值。
2. **裁判提示方差**：宽松的裁判提示可能反转方法排名，作者使用严格的事实性裁判，但绝对分数可能偏低，相对排序也受裁判协议影响。
3. **索引模式扩展性**：虽然AutoMEM结合了索引，但其默认图模式（实体/主题/序列边）仍需针对新场景调整，不一定是可扩展的元学习方案。
4. **动态任务中的处理局限**：在ALFWorld等任务上，所有记忆方法均未显著超过长上下文，说明记忆设计在当前框架下受限于策略能力，需更复杂的机制（如参数后训练）。
5. **评估范围**：未涵盖所有可能的记忆设计（如带预算路由的变体、更多RL方法），也未在更大规模骨干（如GPT-4）上验证结论的迁移性。
6. **部署风险**：若记忆包含用户数据，主动工具调用需要额外安全措施（访问控制、内容过滤、审计日志），论文未详细讨论这些工程实践。
