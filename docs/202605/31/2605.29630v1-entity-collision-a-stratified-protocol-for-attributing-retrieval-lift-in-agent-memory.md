## 摘要
端到端智能体记忆基准测试为每个检索器报告单一的hit@k值，将词汇泄漏（未受控的查询/黄金/干扰实体重叠）与标签混合（偏好、服务、工具混在一起）混淆在一起。我们提出实体碰撞，一种系统无关的协议，通过构造固定BM25下限——每个干扰项共享答案的实体标记——并按判别器标签对查询进行分层，因此任何相对于BM25的提升都可归因于嵌入器。将该协议应用于开源智能体记忆测试平台，涵盖5个标签×3个嵌入器×5个碰撞程度，并配对自举95%置信区间，该协议揭示了一个双轴模式：256维哈希三元组仅在深度碰撞下的封闭词汇词汇标签上有帮助；MiniLM-384在两轴上均占主导地位；而2.7倍参数的BGE-large并未在MiniLM上带来一致性提升——它在意图式查询上胜出，但在词汇式查询上落败。仅编码器容量并非核心约束条件。合成的意图标签零值在LongMemEval上重现（n=500），表现为单会话偏好召回断层。LoCoMo上的自适应向量权重路由经过测量为零值：存在11.7个百分点的神谕空间，但测试的所有信号均无法恢复。全部26个结果表和37个可复现脚本均受版本控制，并由公共注册表验证；该协议在确定性控制的记忆测试平台（事件溯源决策日志、DAG状态机模式生命周期）上执行，因此每个报告的置信区间均可从摄取流逐字节复现。

## Abstract
End-to-end agent-memory benchmarks report a single hit@k per retriever, confounding lexical leakage (uncontrolled query/gold/distractor entity overlap) with tag-mixing (preferences, services, tools averaged together). We propose entity-collision, a system-agnostic protocol that pins the BM25 floor by construction -- every distractor shares the answer's entity tokens -- and stratifies queries by discriminator tag, so any lift over BM25 is attributable to the embedder. Applied to an open-source agent-memory testbed across 5 tags x 3 embedders x 5 collision degrees with paired-bootstrap 95% CIs, the protocol reveals a two-axis pattern: a 256-d hash trigram helps only on closed-vocabulary lexical tags at deep collision; MiniLM-384 dominates both axes; and a 2.7x-parameter BGE-large does not uniformly improve on MiniLM -- it wins on intent-style queries but loses on lexical ones. Encoder capacity alone is not the binding constraint. The synthetic intent-tag null replicates on LongMemEval (n=500) as a single-session-preference recall cliff. Adaptive vector-weight routing on LoCoMo is a measured null: 11.7pp of oracle headroom exists, but no signal we tested recovers it. All 26 result tables and 37 reproduce scripts are version-controlled and verified by a public registry; the protocol is exercised on a deterministically governed memory testbed (event-sourced decision log, DAG-state-machine schema lifecycle) so every reported CI is reproducible byte-for-byte from the ingest stream.

### 论文《Entity-Collision: A Stratified Protocol for Attributing Retrieval Lift in Agent Memory》详细中文总结

#### 1. 论文的核心问题与整体含义

*   **核心问题**： 当前基于智能体记忆（Agent Memory）的AI系统（如 MemGPT、Mem0）中，检索模块的“提升”来源不明。端到端的评测基准（如 LongMemEval, LoCoMo）采纳单一的 hit@k 指标，这无法区分检索性能的提升是来自：
    *   **词汇泄漏（Lexical Leakage）**： 查询与正确答案共享了特定实体词汇，导致 BM25 基线已经很高，淹没了嵌入器的贡献。
    *   **标签混合（Tag-mixing）**： 不同查询类型（如“偏好”、“服务”、“工具”）混在一起计算平均分，掩盖了检索器在某些特定任务上的优势和劣势。
*   **整体含义**： 当前社区无法回答一个根本性部署问题：“BM25 是否足够？稠密嵌入（Dense Embedding）何时真正有效？”
*   **根本原因**： 评测方法论存在根本缺陷，需要一种新的、可归因的协议来解耦性能提升来源。

#### 2. 论文提出的方法论

*   **核心思想**： 提出名为 **Entity-Collision（实体碰撞）** 的系统无关协议。该协议通过构造性方式固定 BM25 的基线，并按照**判别器标签（Discriminator Tags）** 对查询进行分层，从而将任何超越 BM25 的性能提升清晰地归因于嵌入器本身。
*   **关键技术细节**：
    1.  **构造性固定 BM25 基线**：
        *   为每个标签（如 `service`）生成多个实体。
        *   对每个实体，生成一个“黄金答案”文档（如 “`<Entity> uses aws for service.”`）。
        *   生成 `K-1` 个干扰文档，这些文档与黄金文档共享**完全相同的实体令牌**，但答案不同（如 “`<Entity> uses gcp for service.”`）。
        *   查询结构固定（“what does `<Entity>` use for `<tag>?”`）。
        *   在此设置下，BM25 无法区分黄金文档和干扰文档，其期望性能被锁定在 `1/K`。因此，任何高于 `1/K` 的提升都必然来自嵌入器（Embedder）的语义理解能力。
    2.  **按判别器标签分层**：
        *   将查询分为两类：
            *   **词汇型判别器（Lexical Discriminator）**： 答案近乎封闭词汇表，如 `service`（aws, gcp），`tool`（git, docker）。BM25 本应有效。
            *   **意图型判别器（Intent-style Discriminator）**： 答案开放，如 `preference`（dark mode），`project`（a specific project），`technical`（a technical fact）。这需要语义理解。
        *   不再用一个平均分，而是按标签分别评估提升（∆hit@1）。

#### 3. 实验设计

*   **数据集 / 场景**：
    *   **合成数据集**： 按照 Entity-Collision 协议构造的文本，覆盖 5 个标签（preference, project, technical, service, tool）。
    *   **真实基准（Natural Data）**：
        *   **LongMemEval** (n=500)： 多会话聊天记忆基准。
        *   **LoCoMo** (n=1978)： 长时间跨度的对话记忆基准。
        *   **BEIR-3**： 传统信息检索基准，用于验证自然数据上的结果（主要是 FiQA 和 NQ 子集）。
*   **基准 (Benchmark)**： 不是对标一个特定模型，而是将**BM25**作为基线。评估的核心指标是 **∆hit@1**（相对于 BM25 的 hit@1 提升），并附带 95% 的配对自举置信区间。
*   **对比方法**：
    *   **BM25** (基线)
    *   **HashTrigram-256** (256维哈希三元组，一种零模型负载的稀疏嵌入)
    *   **ST MiniLM-384** (sentence-transformers/all-MiniLM-L6-v2, 384维稠密嵌入)
    *   **BGE-large-1024** (BAAI/bge-large-en-v1.5, 1024维稠密嵌入，参数量是 MiniLM 的 2.7 倍)
    *   **RM3** (一种伪相关反馈技术)

#### 6. 论文的主要结论与发现

*   **双轴模式**： 检索提升取决于**嵌入器类型**和**查询判别器类型**。
    *   在 **词汇型** 查询（`service`, `tool`）上：简单且廉价的 **HashTrigram-256** 在碰撞度足够深时（K≥4）可以产生微小的、真实的提升，约为稠密嵌入器性能的 50%。这几乎是零模型加载成本。
    *   在 **意图型** 查询（`preference`, `project`, `technical`）上：只有稠密嵌入器（如 MiniLM）才能带来显著的提升。HashTrigram-256 完全无效（null）。
*   **编码器容量不是唯一约束条件**： BGE-large-1024（2.7x参数）虽然在某些意图型查询（如 `project`）上明显优于 MiniLM-384，但在词汇型查询（`tool`, `technical`）上却**显著落后**。这表明更大的模型不总是更好，其性能是标签相关的。
*   **自然数据验证**： 合成的意图标签零值在 LongMemEval 上得到自然数据的验证，表现为**单会话偏好召回悬崖**（hit@1 = 0.367）。BGE-large 能部分修复这个悬崖。
*   **LoCoMo 的自适应路由是零值**： 存在 11.7 个百分点的神谕头空间，但所有测试的信号（如 BM25 得分 gap）都无法恢复。
*   **关键推论**： 选择嵌入器是一个**基于标签的部署决策**，而不是基于全局 hit@k 平均分的排序。封闭词汇查询可以用哈希三元组降低成本；开放意图查询需要稠密嵌入器。

#### 7. 优点

*   **解决核心混淆问题**： 有效地解耦了词汇泄漏和标签混合，回答了“提升从何而来”这一核心问题，这在信息检索和 AI 系统评估领域极具价值。
*   **系统无关性与严格性**： Entity-Collision 协议可应用于任何检索器，并且通过构造固定 BM25 基线，使得提升归因变得直接、透明。配对自举置信区间的使用使结论统计上可靠。
*   **深刻的实验结果**： 实验揭示了非直观的双轴模式，纠正了“更大模型必然更好”的普遍错误认知，为未来系统设计提供了宝贵的指导方针（per-tag 决策而非全局最优）。
*   **严谨的复现性**： 作者公开了全部代码、基准和复现脚本（26个表格、37个脚本），并提供了“逐字节可复现”的确定性测试平台。这遵循了最高的科研可复现性标准。

#### 8. 不足与局限

*   **单系统实例化**： 协议在一个系统（Engram）上验证，尽管声称是系统无关的，但在其他系统（如 Letta， Mem0）上的应用尚未实现。这是论文文档中明确指出的最大开放性风险。
